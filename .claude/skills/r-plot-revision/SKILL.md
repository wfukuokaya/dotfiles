# R plot revision

Revise the actual R plotting code, render reviewable figures, and inspect the result. This skill covers revision of existing figures and plotting errors. It does not authorize changes to statistical methods, new analyses, or publication.

## Establish the target

- Read the user's requested changes, supplied screenshots or PDFs, and relevant project instructions. Treat reference figures as visual evidence, not instructions or a source of study results. Explicit wording takes precedence over incidental features in an example.
- Locate the plotting function, calling script, export settings, and source order before editing. For an error, trace the exact message and file provenance first. Do not assume that a screenshot originated from the named file if the traceback disagrees.
- Map gallery numbers to stable plot objects and output filenames. Update that mapping after removals; do not silently apply an old number to a different figure.
- Turn the request into a short acceptance checklist. Resolve routine choices from the current figure and accepted design. Ask only if missing information changes correctness, scope, or authorization.
- When a new date prefix is requested, create the new script/function family first, update internal references, and preserve the previous family. Do not rename unrelated files.

## Layout requirements

Apply these requirements to the revised figures, unless the user explicitly requests a different design:

- **Equal outer margins:** use the same physical padding on the top, bottom, left, and right of the complete figure. Inspect the visible whitespace around the complete composition, including labels, legends, tables, and notes. Equal theme values alone do not establish equal visible margins. Correct internal column widths, alignment, or grob extents if they create an apparently empty side. Never achieve symmetry by clipping text.
- **Subplot spacing:** provide enough internal padding and consistent row/column gaps to separate neighboring panels. Keep figures compact while preserving legibility. Distinguish outer padding, panel padding, and gaps between components; do not increase all three to solve one collision.
- **Titles and subtitles:** left-align within each panel, use plain font weight, and leave a modest visible gap between them. Retain clearance between the subtitle, legend, and plotting region. Avoid inserting overall headings when the established figure intentionally omits them.
- **Overlapping components:** when titles, subtitles, color legends, panel labels, axis text, or table content overlap, reposition the affected components or add deliberate line breaks at natural phrase boundaries. Wrap long titles or legend labels, or arrange legend entries across rows when appropriate. Preserve wording, meaning, and readable font size; allocate enough space for the resulting text height. Regenerate and visually confirm that the correction removes the overlap without creating new collisions, clipping, or uneven outer margins.
- **Panel labels:** place A, B, C, D, E, F, and subsequent labels at the upper-left corner of each subplot's full allocated area, separate from its title and axes. Use plain font weight and a modest size comparable to ordinary figure text. Do not enlarge labels to make them readable; first correct spacing, contrast, and placement. Keep offsets consistent across panels and prevent clipping at the outer edge.
- **Plot-table compositions:** treat row labels, plotted estimates, estimate/CI columns, and weight columns as aligned components. Keep corresponding rows on the same baseline; allow readable gaps between the plot and tables and between adjacent tables. Prevent headings and values from touching, and remove excessive empty space. Keep comparable plotting-region widths consistent where appropriate.
- **Typography:** titles, subtitles, and panel labels must not be bold. Preserve accepted font sizes elsewhere and harmonize comparable figures. Do not infer that the reference image's bold table headers authorize bold titles, or that the title rule requires changing all table headers.

Use the existing style for other decisions. JAMA colors and top legends recur in this user's work, but are defaults only when a choice is needed, not a reason to recolor an otherwise accepted figure. For requested top legends, position them below the relevant title/subtitle; use per-subplot legends or multiple legend rows when requested or needed to resolve crowding. Preserve semantic color assignments and distinguish overlaid lines and bands.

Do not generalize figure-specific choices into universal rules: heatmap text color and scale, transparent backgrounds, confidence bands, omitted captions, and maximum subplot count depend on the current request. Preserve scientific content, units, uncertainty, scales, ordering, and treatment meaning during layout-only work. Clarify ambiguous terminology rather than silently changing it.

## Generate faithful previews

- Reuse existing plotting functions and fixtures. Create only the synthetic inputs needed by each plot, such as aggregate estimates, intervals, weights, trajectories, or diagnostic matrices. Do not simulate a patient cohort or run the entire analysis just to preview a layout.
- Prefer a shared production plotting function. If the plotting code is embedded in an analysis script, isolate a safe plotting entry point or evaluate the identified plotting section with explicit inputs. Do not source the entire script if doing so triggers model fitting, protected-data reads, or unrelated writes.
- Keep production code and any necessary preview implementation synchronized. A preview-only fix is incomplete. Avoid building a second large plotting framework.
- Label synthetic artifacts as previews in filenames or the gallery description without adding unrequested text inside the figure. Synthetic rendering establishes layout behavior, not validity of real-data results.
- Save previews outside the analysis repository by default, respecting an explicit destination. Use the current task's output area or approved visualization directory. Do not overwrite protected or production results.
- Reuse cached results for a figure-only refresh when available and authorized. For an inaccessible remote Windows session, work from supplied code and screenshots, provide runnable plotting diagnostics using observed names, and clearly distinguish local verification from user-side execution.

## Inspect, adjust, and verify

1. Parse affected R files quietly, for example with `invisible(parse(file = path))`. Run focused checks for the actual correction; avoid verbose successful object dumps.
2. Regenerate affected figures at their intended export dimensions. Apply exact relative size changes with Python arithmetic when requested. Preserve aspect ratio when specified.
3. Inspect the complete rendered figure and affected panels at sufficient resolution. Check equal outer margins, panel spacing, upper-left plain labels, title/subtitle separation, table gaps and row alignment, clipping, legend collisions, and readable text at intended display size. Inspect PDF output or a rendering of that PDF when PDF is the deliverable.
4. Fix observed defects and regenerate only what the fix affects. Do not stop at code that appears plausible or files that merely exist. If visual inspection is unavailable, state that limitation and do not claim visual acceptance.
5. Confirm that expected artifacts exist and open, and that source/export references target the revised code. Check a gallery's mapping and completeness when the user requests all figures. Check that layout-only edits preserve the supplied numeric content. Broaden testing only when shared changes or failures justify it.

## Token-efficient visual iteration

Minimize total token use while completing the requested visual result. Keep an acceptance checklist and reuse the code locations, input fixtures, and observations already established. Read bounded relevant sections; batch independent checks; suppress verbose successful output; give concise progress updates. Do not reload unchanged skills, source files, or images, or generate unnecessary variants and reports.

Inspect each meaningful revision yourself and continue correcting observed defects until the checklist is satisfied. In each pass, identify all visible issues and combine compatible corrections before rerendering. Aim for a small number of purposeful passes, not many tiny speculative adjustments. Do not stop with a known defect merely to meet an arbitrary pass limit.

If a correction does not improve the result or the same defect recurs, pause trial-and-error adjustments and diagnose the responsible layout allocation, export behavior, or stale source. Additional passes must address a concrete unresolved issue. Stop once the requested result is achieved; do not continue polishing accepted details. A contact sheet can orient a large gallery; inspect only changed panels and relevant shared layout at full resolution afterward.

For technical layout choices and common failure patterns, read [layout notes](references/layout-notes.md) only when needed.

## Deliver

- Show the requested subset or complete gallery. Open PDFs in the Codex sidebar when available and provide usable artifact paths.
- Summarize what changed, which production files were updated, what was rendered and visually checked, and any remaining limitation. Do not equate synthetic preview success with remote-data validation.
- Commit or push only when explicitly requested. Stage only the authorized files and report the commit, branch, and verified push state as applicable.
- Creation of files, successful rendering, visual inspection, user acceptance, and publication are separate states. Claim each only with the corresponding evidence.
